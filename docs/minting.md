# Minting jobs

E04 runs minting in two modes:

- Requests at or below `MINT_SYNC_MAX` (5,000 in compose) run synchronously in
  the API process.
- Larger requests are recorded as a `mint` BullMQ job and return a job id. The
  `api-worker` process consumes that job and the follow-up `batch-exports` job.

## Local processes

The Docker stack uses the same `apps/api` image for both processes:

```sh
docker compose -f docker/compose.yml up -d
docker compose -f docker/compose.yml logs -f api-worker
```

`api` is the HTTP process and has `WORKER_INLINE=false` in compose. `api-worker`
has `WORKER=true` and `WORKER_INLINE=false`, runs
`node apps/api/dist/worker.js`, publishes no host port, and waits for Postgres,
Redis, and MinIO. The worker entrypoint creates a Nest application context
containing the queue connection and job providers only; it does not start an
HTTP listener.

For `pnpm dev`, `WORKER_INLINE` defaults to `true`. This keeps local development
single-process until the compose worker is started. When testing the split
processes locally, set `WORKER_INLINE=false` on the API and run the built worker
entrypoint separately.

## Queues and restart behavior

BullMQ uses the shared `REDIS_URL` connection and registers these queues:

- `mint` — generates units in `MINT_CHUNK` chunks (1,000 in compose), updates
  job progress, and generates the encrypted manifest when complete.
- `batch-exports` — generates QR, CSV, PDF, and ZIP artefacts from the manifest.

Each mint chunk commits its units and advances the batch resume pointer in the
same workflow. If `api-worker` is restarted, BullMQ redelivers the job and the
processor resumes from the batch's last completed chunk. Start or restart only
the worker while preserving the per-worktree environment generated by
`scripts/epic start`; do not hard-code host ports.

## Tier-2 handling

Tier-2 codes are generated in worker memory, hashed before units are persisted,
and written only to the encrypted `manifest.json.enc` object. The manifest is
decrypted in-process when exports need the codes; the worker does not expose a
manifest HTTP route or write raw tier-2 values to logs, CSV, or the database.

E03 and E06 can add their BullMQ processors to the worker module/queue graph.
They should publish their queue name and processor provider through their epic's
module, keep `WORKER_INLINE=true` as their pre-worker fallback, and use the
existing `api-worker` service rather than adding another published port.
